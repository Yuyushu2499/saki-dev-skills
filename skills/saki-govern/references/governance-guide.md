# 文档保鲜、测试分层控频、Worktree 治理与静态检查指南

本文配合 `saki-govern` 使用，总结长期复杂项目保持干净、快速、不腐化的核心方法。

## 1. 文档与规范治理：单源减负与事实保鲜

- **多工具入口单源同步**：项目级通用红线统一维护在根目录 `AGENTS.md`（Antigravity 原生支持读取 `AGENTS.md`，无需另建重复的 `GEMINI.md` 以免重复加载消耗上下文）；团队同时使用其他读取特定入口文件名的宿主工具（如 Claude Code 读取 `CLAUDE.md`）时，把对应入口文件写成单行 `@AGENTS.md`，既防止漏加载规范，又避免两份拷贝改漏一边。
- **把 `AGENTS.md` 当成「项目地图与按任务路由表」（建议 `4–8 KB`，超过 `10 KB` 必拆；Antigravity 单文件上限为 `24 KB`）**：`AGENTS.md` 在每次新开对话时都会无条件加载，哪怕表面只有百来行，只要把单一业务的禁词清单、配色细节、CLI 参数说明堆成几百字的超长自然段，每次改一行普通代码也要白白消耗大量上下文。合格的 `AGENTS.md` 只保留四块内容：
  1. **核心目录与按任务规范路由表（渐进式加载）**：简要说明核心目录职责，并列出“改哪类任务前必须先读哪份专题文档或项目内 Skill”（如改界面读 `DESIGN.md`、动支付鉴权读 `docs/architecture.md`、跑特定渠道发布读 `.agents/skills/<name>/SKILL.md` 或 `.agents/plugins/<name>/`），让无关任务不再预加载大段细则；
  2. **跨全仓通用的协作与发布红线（控制在 5 条以内）**：只放所有任务都适用的底线（例如职责分工、收到上线指令必须走分支 + PR 合并流程而严禁直接 push `main`、触发群发或外部写操作前必须经人确认等）；
  3. **高频入口命令速查**：只列脚本入口与一句话用途，长串参数留在脚本 `--help` 或专题文档；
  4. **`## 开发约定（saki-dev）`**：10 行以内固定快测、重测、门禁、高风险与禁改目录，供探索、方案、审查与禁改拦截钩子直接读取。
- **消除跨文档与项目内 Skill 的多头重复抄写**：长期项目很容易在 `AGENTS.md`、`DESIGN.md`、专题文档以及 `.agents/skills/*/SKILL.md` 里把同一段规则各粘贴一遍。治理时必须去重收拢——每条细则只留一份唯一权威单源，项目内 Skill 与 `AGENTS.md` 只写流程骨架并用相对链接指向该单源文档，再靠相对死链检查保证引用不断裂。
- **规则生命周期（严进、转脚本、常删）**：偶发单点问题不写进 `AGENTS.md`（仅当同类坑重复出现 `>= 2–3` 次且跨模块通用时才补一行精炼红线）；凡能写成静态单测、lint 或构建门禁自动拦截的规则，代码落地后同步删掉 `AGENTS.md` 里的长篇文字叮嘱；业务定价、环境变量或架构演进后及时清理失效旧条文。
- **清理一次性过程快照与建立模块路由**：多轮代码审查清单、早期原型计划与临时验收日志，在阶段收尾后及时删除或归入 `docs/archive/`，避免检索时混入过期结论；对长期未动的 `README.md`、`DESIGN.md` 与架构文档，定向核对配置开关、基线版本与目录树是否与代码冲突。跨多层或多端的大仓库若探索频繁反复翻找调用链，可在 `docs/` 维护一份精简的「核心功能 → 模块入口映射表」并从 `AGENTS.md` 路由表链接过去（只写入口路径与一句话职责，单源维护）。

## 2. 测试治理：快慢分层、量化预算与重构建控频

### 测试分层、耗时预算与触发频率（防快测悄悄变慢）
在真实长周期项目中，如果不加约束，一方面 AI 执行器容易“改代码 10 次、跑测试 70 次”，另一方面原本秒级的快测清单会随迭代越塞越多，最终退化成几分钟的中重测。治理时必须从入口、预算和规则三头兜住：

1. **快测层（秒级局部反馈，全跑预算 ≤ 30 秒）**：提供按类名、文件名或 `git diff`（如 `--changed`）自动缩圈的局部快测入口。实测快测全跑超过 30 秒或清单持续膨胀时，立刻把慢用例迁出重测层，并把多条串行子命令合并或改为并发执行器。编码途中只跑编译、类型检查或 lint，整轮改完跑局部快测。
2. **重测层与重构建控频（收尾或合并前统一跑一次）**：端到端（E2E）、媒体/大算力回归、跨模块全量测试、原生重型子产物冷编译与完整安装包打包，通过独立命令或开关隔离，**绝不混入日常默认快测**。在 `saki-dev` 开发约定里标出 `重构建` 触发目录，未改到这些目录时默认复用已有构建产物，不反复冷编。若项目打包耗时高或依赖远程/独占测试环境，建议在仓库脚本中单独提供增量同步或局部替换的轻量验证入口，把完整打包与安装卸载验证保留在合并门禁。
3. **排查慢单测与孤儿测试**：
   - 检查测试耗时 Top N，把混在普通单测里却耗时十几秒以上的重计算/重 I/O 用例优化或移入重测层；
   - 检查 `scripts/tests/` 等辅助测试目录是否真挂进了主测试入口或 CI，避免写出从不执行的“孤儿测试”。CI 里实际执行的命令（快照中的 `ci_run_steps`）是最可靠的依据。
4. **新增黑盒或端到端套先小样本校准再扩量**：跨进程、界面或真实环境测试套首次建立时，先挑 3–5 个覆盖主链路的代表性用例在目标环境（真实区域与编码、权限与文件锁，涉及界面时含缩放比例与字体环境）跑通并确认零用例间串扰，再批量扩充；未经校准的新增整批测试不得直接作为阻断门禁。

### 清理低价值测试与守住无副作用底线
- **删除假测试与过拟合脆性测试**：清理重度 mock 内部调用只测假返回值、零实质断言或靠硬写 `sleep` 等待的假测试；同时清理把易变实现细节写死的脆性测试（如逐字断言本地化自然语言报错文案而非错误码/类别，或多个用例争用同一全局锁/共享路径导致单点异常引发整批连锁误报）。
- **无副作用隔离**：所有自动化测试必须无头静默运行——不抢桌面焦点、不弹系统权限框、不读写用户真实的生产配置域或最近打开记录。

## 3. 并行 Git Worktree 与分支卫生

复杂项目常开多个 Worktree 并行推进不同特性，治理时重点检查三件事：
1. **禁止嵌套在主仓库目录内**：子 Worktree 统一建在主仓库同级的父目录下（若工具建在隐藏子目录内，确认已被 `.gitignore` 覆盖），防止外部文件扫描把两份仓库和两份构建目录混在一起。
2. **复用热编译缓存与回收已合并工作树**：对已合入主干的 Worktree，优先在其上直接切新分支复用已有编译产物（在支持写时复制的文件系统上新建 Worktree 时也可克隆主仓库构建缓存），不再使用的及时执行 `git worktree remove` 与旧分支清理。判断“已合入”时注意：
   - 只看“分支是不是主干的祖先”会出两种错：squash 合并的分支永远不是祖先，会被漏掉；刚建还没提交的分支天然是祖先，会被误判为已合入。
   - 快照因此把状态分成：普通合并（`merged`）、squash 合并（`squash_merged`，按整体补丁指纹比对）、rebase 合并（`rebase_merged`，每个提交都能在主干找到等价补丁）、没有独立提交（`no_own_commits`）与未合入（`unmerged`）。
   - 只有前三种且没有未提交改动的才标为可清理候选；`no_own_commits` 先问用户；清理前一律列清单征得确认。
3. **保持主干工作区干净**：并行开发期间避免在 `main` 主工作区直接堆积大量未提交修改，减少合并冲突。

## 4. 把硬规则落地为仓库内静态检查

Skill 规则只对读取它的 Agent 生效；换用其他编排器、外部 CLI 或人工提交时，真正能 100% 拦住回归的是**目标仓库自带的确定性静态门禁**。体检发现同类问题反复发生时，优先往仓库的静态检查入口落地以下四类通用守卫（按项目实际按需选用，落地后删除文档里的冗长文字叮嘱）：

1. **代码文件行数棘轮检查**：新建源码文件不超过约定上限（如 `saki-dev` 的 `文件上限`）；存量已超限的历史大文件写入基线清单，只允许持平或下降、禁止继续净增（自动排除生成文件、锁文件与纯数据文件），从根上阻止巨文件越滚越大。
2. **测试分层与快测预算检查**：校验新增测试已登记到正确的快/重分层清单，快测清单不含耗时/副作用特征，并定期输出慢用例排行防止快测层慢性膨胀。
3. **版本、清单与多语言/文档一致性检查**：静态比对构建版本号、最低兼容版本声明、多语言词条配对、打包清单必需资产与文档基线引用，消除“改了一边漏另一边”导致的正式产物故障。
4. **跨平台与重构建缓存守卫**：静态扫描跨平台脚本中的硬编码路径分隔符或单平台假设；为重型构建脚本加入输入哈希校验，输入未变时自动跳过冷编译并复用已有产物。

# saki-govern

`SKILL_DIR` 指当前 Skill 的绝对目录；`<python>` 指 Python 3.10+（macOS/Linux 通常为 `python3`，Windows 通常为 `py -3`）；`AUDIT_REPO` 是 `<python> "$SKILL_DIR"/scripts/audit_repo.py` 的简写。

## 核心规则

- **脚本只采客观事实，语义判断交给模型**：先运行轻量脚本 `AUDIT_REPO` 秒级获取文档死链与新鲜度、常驻规范与项目内 Skill/Plugin 体积、Git 演进温差、超大活跃文件、CI 实际执行的命令与 Worktree 合入状态，不在通用脚本里堆砌生硬的硬编码正则；拿到客观数据后再定向阅读具体文件做准确判断。
- **`AGENTS.md` 只做路由入口，单源维护、严进常删**：把 `AGENTS.md` 控制在 `4–8 KB`（超过 `10 KB` 必拆；Antigravity 单文件硬上限为 `24 KB`，所有常驻规则共享 `20,000` tokens 预算），只留「核心目录与按任务规范路由表 + 全局协作与发布红线 + 常用入口命令 + `saki-dev` [开发约定](references/dev-profile.md)」四块；单一领域细则下沉到专题文档或项目内 Skill 按需读取，严禁在 `AGENTS.md`、`GEMINI.md`、专题规范与项目内 Skill 之间多处重复抄写同一批规则。Antigravity 原生支持读取 `AGENTS.md`，不需要另建重复的 `GEMINI.md`；其他只认特定文件名的宿主（如 `CLAUDE.md`）统一用单行 `@AGENTS.md` 引用。
- **测试与构建双控频、量化防膨胀**：把秒级局部快测与高耗时重测拆开，在 `AGENTS.md` / `GEMINI.md` 明确快测耗时预算（默认目标 ≤ 30 秒，优先支持按改动缩圈）、重构建触发目录与文件上限；定期把悄悄变慢的用例迁出快测层，排查孤儿测试并守住无副作用隔离。
- **专属规矩落地在目标项目内部**：Skill 只是软流程，凡能静态判定的硬约束（代码文件行数棘轮、快测防膨胀、架构禁引、版本与多语言一致、跨平台路径安全、打包资产清单），写成**目标仓库自己的**确定性静态检查接入构建门禁，让任何执行器都会被仓库自己拦住，落地后删掉常驻文档里的长篇文字叮嘱。

## 先选择模式

| 模式 | 适用情况 | 路径 | 默认停止点 |
| --- | --- | --- | --- |
| 全仓体检 | 阶段性维护，快速盘点文档、测试与 Worktree 现状 | `AUDIT_REPO --scope all` → 定向抽查热点文件 → 输出分级整改清单 | 呈现客观问题清单请用户勾选 |
| 文档与规范治理 | 同步入口规则、清理过期描述/死链、归档过程快照、建立或校准开发约定 | `AUDIT_REPO --scope docs` → 对照近期活跃代码核查核心文档 → 更新瘦身 | 常驻文档准确清爽、零死链且开发约定可用 |
| 测试分层与瘦身 | AI 跑测试太频繁太慢、存在孤儿/无效测试或漏测盲区 | `AUDIT_REPO --scope tests` → 拆分快慢入口 + 写控频规则 + 清理慢/假测试 | 跑通快测入口并确认重测分层 |
| 分支看板 | 想知道各分支和工作树在哪、推没推、进没进主干、改了什么，本地和云端是否一致 | `AUDIT_REPO --scope board --fetch --json` → 读未合入分支的改动并给建议 → 画出或写出看板 | 交付看板，等用户选择下一步 |
| Worktree / 脚本化 | 清理并行工作树、把文字规矩写成项目内静态检查 | 盘点 Worktree / 编写项目内检查测试 | 完成清理或接入检查 |

## 工作流

### 1. 采集客观治理快照

动手修改前先运行只读采集脚本（支持 `--scope all|docs|tests|worktrees|board` 与 `--json`）：

```text
AUDIT_REPO --workspace "<项目路径>" --scope all
```

### 2. 文档与 `AGENTS.md` / `GEMINI.md` 治理

结合快照中的 `docs` 与 `code_and_tests.top_dir_recent_commits`，对照 [治理实操指南](references/governance-guide.md#1-文档与规范治理单源减负与事实保鲜) 定向检查：

1. **多宿主入口单源同步与 `AGENTS.md` 路由化减负**：检查是否同时存在内容重复的 `AGENTS.md` 和 `GEMINI.md`（若重复则收拢到单一 `AGENTS.md`，避免 Antigravity 重复加载浪费上下文），检查其他宿主规则入口（如 `CLAUDE.md`）是否统一用单行 `@AGENTS.md` 引用；若 `AGENTS.md` 超过 `8–10 KB` 或混入了大段单一业务细则，按「核心目录与按任务规范路由表 + 全局协作与发布红线（如严禁直接 push `main`、必须走分支 PR 合并） + 常用命令速查 + `saki-dev` 开发约定」四块结构重写，把写作、设计、支付、渠道发布等局部细则下沉到专题文档，并在路由表里指明“做哪类任务时先读哪份文件”。
2. **消除跨文档与项目内 Skill/Plugin 的重复抄写**：对照专题规范（`DESIGN.md`、`docs/*.md` 等）与项目内自定义 Skill/Plugin（`.agents/skills/`、`.agents/plugins/`、`.agent/`、`.claude/skills/`、`.codex/skills/`），排查是否把同一套长规则在 `AGENTS.md`、专题文档和 `SKILL.md` 里各抄了一遍；统一收拢到唯一权威单源文档，其余入口改为相对链接按需引用，并修复全部相对死链。
3. **核查核心文档的事实性过期与过程快照清理**：快照按最久未修改列出文档距今的提交数与天数。若源码持续演进，而 `README.md`、`DESIGN.md` 或架构文档长期未动，重点核对其中的定价、环境变量开关、目录树、不做边界与工具链描述是否已与代码矛盾；将根目录或 `docs/`、`review/` 中早期原型阶段遗留的废弃计划、单次验收流水账删除或归入 `docs/archive/`。
4. **建立校准开发约定与规则新陈代谢**：快照提示“未找到开发约定”、缺少必填项或高风险目录失配时，按 [开发约定格式与生成指南](references/dev-profile.md) 起草或修订（快测命令实际跑一次确认够快），经用户确认后写入 `AGENTS.md`（若项目以 `GEMINI.md` 为主则写入 `GEMINI.md`）；已被静态测试或构建门禁接管的旧文字叮嘱同步精简或移除。

### 3. 测试分层、控频与质量治理

结合快照中的 `test_directories`、`defined_scripts` 与项目实际测试脚本，对照 [测试分层与瘦身指南](references/governance-guide.md#2-测试治理快慢分层量化预算与重构建控频) 处理：

1. **快慢分层、量化预算与触发频率约束**：确认仓库具备按模块、文件或 `git diff`（如 `--changed`）缩圈的**秒级局部快测入口**，以及独立隔离的高耗时重测入口；快照提示快测命令未带过滤参数，或实测快测全跑已超过 30 秒时，提议拆出慢用例或补按改动筛选能力。在 `AGENTS.md` 写清“编码途中只跑秒级检查，改完跑局部快测，未改重构建目录时复用缓存，全量与打包门禁留到收尾或合并前统一跑一次”。
2. **排查孤儿测试与慢单测混入**：以快照里的 `ci_run_steps`（CI 实际执行的命令）和已定义脚本为准，逐个核对测试目录是否真被某条命令执行到，没被任何入口覆盖的就是孤儿测试候选；快照提示“未发现 CI 配置”时，如实说明无法客观确认，只能对照本地测试入口判断。若有耗时几十秒的重计算用例混在普通单测层，提议抽离或优化。
3. **先小样本校准再扩量，并清理脆性测试**：新建跨进程或端到端黑盒测试套前，先在真实目标环境跑通少量代表性用例确认无环境失配或共享状态串扰，再扩量纳入拦截；清理零业务断言、重度 mock 自证、硬写长 `sleep`、硬编码本地化提示文案或共享锁引发连锁误报的脆性测试，并确认自动化测试全程无头静默、不污染用户真实配置域。

### 4. 分支看板

阅读 [分支看板](references/branch-board.md)，按其中的分组、说法和版式执行：

1. 运行 `AUDIT_REPO --workspace "<项目路径>" --scope board --fetch --json`。没有网络时去掉 `--fetch`，并说明云端状态可能不是最新的。
2. 对“需要你决定”和“正在进行”里的每条分支，读它的提交和主要改动，用一句用户听得懂的话说清改了什么，再给出建议和理由。
3. 在 Antigravity 等支持对话内渲染界面的宿主里，优先使用 `generative_ui` 技能画出交互式分支看板；不支持时用参考里的 Markdown 模板；两种呈现的内容和顺序相同。
4. 推送、合并、删除分支或清理工作目录，都等用户选择后再做。

### 5. Worktree 卫生与项目内脚本化

- **并行 Worktree 与分支清理**：若快照显示子 Worktree 直接嵌套在主仓库目录内，建议移至同级父目录或加入忽略规则。按快照里的合入状态区别对待：
  - 标为“可清理候选”的（普通合并、squash 或 rebase 合入，且没有未提交改动）：提示直接切新分支复用其热编译缓存，或移除回收空间。
  - 标为“没有独立提交”的：可能是刚建还没开工，也可能已快进合并，脚本无法区分，先问用户。
  - 有未提交改动的：一律不清理，先告诉用户有哪些改动。
  - “远端分支已删除”只是辅助信号，不能单独作为清理依据。
  - 执行 `git worktree remove` 或删除分支前，列出清单并征得用户确认。要删的分支或工作树带有未合入的提交时，先派发只读子 Agent **`saki-reviewer`**（未注册时用 `research`）核对这些提交是否已在别处保存、删了能不能找回，再请用户确认。
- **项目硬规则转静态测试**：阅读 `AGENTS.md` / `GEMINI.md` / `DESIGN.md` 中的明确禁令与高频翻车点，按 [治理实操指南](references/governance-guide.md#4-把硬规则落地为仓库内静态检查) 在**目标仓库的测试套或 `scripts/`** 中落地确定性静态检查（如文件行数棘轮、快测防膨胀、版本与清单一致性、跨平台路径与打包资产检查），确保不依赖特定 Agent 或 Skill 也能自动拦截。
- **单个顽固缺陷不在这里处理**：连修两轮仍卡住的缺陷，交给 `saki-bug-fix` 的止损步骤。`saki-bug-fix` 提议把某类普遍问题写成自动检查、用户同意后，由本 Skill 编写。

## 输出与后续衔接

体检阶段只输出有确切依据的事实清单与优先级建议；用户确认要改的项后再落盘修改并验证。

| 下游意图 | 衔接动作 |
| --- | --- |
| 将某条硬规矩落地为目标仓库内的静态测试后清理旧审查项 | 配合 `saki-code-review` 删掉重复的人工审查规则 |

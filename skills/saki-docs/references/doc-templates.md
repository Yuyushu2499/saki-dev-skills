# 项目活文档体系与写作模板

本文配合 `saki-docs` 使用，遵循 **Docs as Code（文档即代码）** 与 **Living Documentation（活文档）** 原则：文档描述系统**当前的真实状态**，默认使用简体中文（除非用户指定其他语言），按需生长，绝不造空壳文件。

---

## 1. 通用写作红线（反模式清单）

1. **零脑补、零虚构**：所有命令、路径、配置项、环境变量、接口字段必须来自代码或配置文件的实证；代码里看不出来的业务背景标为 `[待补充]`。
2. **不把代码原样抄成文字**：不要逐行翻译函数实现；写清**职责、输入输出、边界条件、依赖方向和为什么这样设计**。
3. **相对链接优先**：在文档里引用仓库内代码或文档时优先使用相对路径（如 `src/export/runner.py`），方便 `saki-govern` 自动检查死链。
4. **增量维护克制 diff**：更新已有文档时只动与本次改动相关的章节，保留作者原有措辞与排版结构。

---

## 2. 核心必选文档（2 件套）

### 2.1 `README.md`（入口与快速上手）
面向第一次打开仓库的开发者或用户，控制在 1–2 屏内读完核心信息：
- **项目简介**：2–3 句话讲清解决什么问题、面向谁。
- **核心功能**：3–6 条要点，只写当前已实现的真实能力。
- **环境要求与快速开始**：运行时版本、安装命令、启动/开发命令（以清单和 CI 实证为准）。
- **常用命令**：测试、类型检查、Lint、构建打包命令速查表。
- **目录结构**：顶层核心目录 + 一句话职责（不展开到每个小文件）。
- **文档导航**：相对链接指向 `docs/architecture.md` 及已存在的按需专题文档。

### 2.2 `docs/architecture.md`（系统架构全景）
中途接手项目时最有价值的地图：
- **系统概览与边界**：整体形态（CLI / Web / 桌面 / 后端服务 / 插件）及与外部系统的交互边界。
- **核心模块职责表**：`目录或入口路径` | `职责` | `依赖方向`。
- **核心数据流 / 调用链**：按 [文档绘图引擎规范](diagram-providers.md) 结合复杂度智能推荐并确认使用 **ExcalidrawZ MCP**（复杂架构全景/拓扑图）或 **Mermaid**（轻量流程/时序图）或已扩展绘图工具呈现 1–3 条主干链路，关键节点附 `路径` 或入口符号名。
- **关键外部依赖与运行时约束**：数据库、外部 API、文件系统、权限或平台差异。

## 3. 按需生长文档（4 类，有才建）

### 3.1 `docs/api.md` 或 `docs/data-model.md`（接口、CLI 与数据契约）
仅当项目存在对外 HTTP/RPC API、CLI 子命令/参数、配置文件 Schema 或持久化存储格式时创建：
- **接口 / 命令清单**：路径/命令、输入参数、输出结构、错误码或退出码约定。
- **配置与环境变量**：名称、默认值、作用与是否敏感。
- **数据模型与兼容约束**：核心实体字段、版本字段与迁移注意事项。

### 3.2 `docs/modules/<模块名>.md`（复杂子系统专题）
仅当单个子系统逻辑复杂、`docs/architecture.md` 写不下时拆分：
- 模块目标与边界（负责什么、不负责什么）。
- 入口文件、核心状态流转或关键不变量。
- 常见扩展方式（如新增一种适配器/插件需要改哪几处）。
- 对应的测试文件与局部快测命令。

### 3.3 `docs/decisions/NNN-<主题>.md`（极简 ADR 架构决策记录）
仅当出现重大技术选型或影响长期演进的取舍时创建，控制在半页内：
```markdown
# NNN. <决策标题>

- **状态**：已采纳（YYYY-MM-DD）
- **背景**：遇到了什么问题或约束？
- **决定**：最终选择了什么方案？
- **放弃的备选与理由**：为什么没选方案 B？
- **影响与代价**：带来了什么收益，接受了什么取舍？
```

### 3.4 `CHANGELOG.md`（变更记录）
仅当项目对外发布版本或仓库已存在该文件时维护，按“新增（Added）/ 变更（Changed）/ 修复（Fixed）/ 破坏性变更（Breaking）”精炼记录用户可见变化，不抄写琐碎 commit 流水账。

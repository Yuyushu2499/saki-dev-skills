# saki-plan

`SKILL_DIR` 指当前 Skill 的绝对目录；`<python>` 指 Python 3.10+（macOS/Linux 通常为 `python3`，Windows 通常为 `py -3`）；`PREFS` 是 `<python> "$SKILL_DIR"/scripts/preferences.py` 的简写，读写本机个人偏好 `~/.saki-dev/preferences.md`。`REVIEW_HELPER` 指 `saki-code-review` Skill 自带的改动采集脚本 `review_helper.py`，用法见该 Skill；未安装时用 `git status` 与 `git diff --stat` 对照契约代替。

## 核心规则

- **默认纯 Antigravity 内部闭环**：方案挑刺、代码实现、子 Agent 执行与重要操作前检查**默认全部使用 Antigravity 原生子 Agent**（`invoke_subagent` 配合插件内置的 `saki-explorer` / `saki-reviewer` / `saki-coder`），不自动触发 `saki-delegate` 或外部 CLI。**只有在用户在对话框中显式点名外部 CLI**（如“让 codex 挑刺”“用 claude 实现”）时，才通过 `saki-delegate` 委托，并遵循其模型弹窗确认流程。
- **按复杂度分级，拒绝小事大做**：不给两三行明确修改强塞长篇方案文档；按 `L1 / L2 / L3` 选择最轻量的对齐方式。
- **方案审查就在本阶段闭环**：审方案属于 `saki-plan` 内置动作，不混入 `saki-code-review`（后者只审已写出的代码）。
- **必须写成用户看得懂的话**：读者无需关心底层框架内部写法，读完就能清楚知道“外部表现有什么变化、动哪几块与复用什么现成基建、本期不做什么、异常边界与怎么验收”。拒绝术语黑话、空话套话和大段实现代码堆砌。
- **事实核实 + 分歧清零后才动手**：不搞填表式的虚假百分比打分。动手前只卡两条真红线：① 提到的现有文件路径、可复用组件与测试命令已在仓库真实核对存在；② 影响用户体验或范围边界的关键分歧已向用户问清。
- **修缺陷先复现**：无论哪个级别，修缺陷都先复现问题（能写失败测试就先写，并确认它真的失败），修完以同一个用例转绿作为验收。
- **子 Agent 模式由用户开启**：用户在本次对话里要求，或个人偏好的 `## saki-plan` 一节写了要用时进入。开启后主 Agent 只拆任务、写契约、拍板和验收，探索、实现、排查、审查、跑门禁全部交给子 Agent，再小的执行也不自己做；开不了子 Agent 时告诉用户，不悄悄自己执行。细则见 [子 Agent 模式](references/subagent-mode.md)。
- **重要操作前先独立检查**：合进主干、批量删除文件、删除带有未合入提交的分支或工作树、改写已推送的历史（强制推送、`reset --hard`、rebase）、改数据格式或数据库结构、打包发布或改对外接口之前，先用 `invoke_subagent` 派发只读子 Agent **`saki-reviewer`**（未注册时用 `research`）回答三个问题：会影响什么、能不能撤回、有没有漏掉的东西。再把它的结论和具体操作一起交给用户确认。
- **派发契约锁死方向、模块边界与控频节奏**：交给子 Agent、当前会话自己实现或用户显式指定的外部 CLI 时，把方向、必复用组件、允许修改的文件、**防大文件堆叠红线**以及**测试与重构建控频规则**一次写死，防止发散、把独立新逻辑塞进巨文件，或反复空跑重测试与全量冷编。

## 先按复杂度分级（L1 / L2 / L3）

| 级别 | 适用场景 | 执行方式 | 默认停止点 |
| --- | --- | --- | --- |
| **L1 轻量直达** | 单模块明确修补、改文案、调样式、原因和改法都清楚的小缺陷（原因不清楚时交给 `saki-bug-fix`） | 2–3 句话说明改法（缺陷先复现）→ 直接修改或派发 → 跑一次关联局部快测 | 完成修改与快测反馈 |
| **L2 对话方案** | 常规单功能开发、中等重构或存在 1–2 个产品取舍 | 核实代码事实 → 在对话里给出精炼四要素方案与待拍板项 → 用户点头后实现 | 用户确认方案（或继续派发实现） |
| **L3 里程碑规格** | 跨多子系统改造、新数据格式/打包链路或高风险架构变更 | 核实事实 → 按项目既有风格写入 `docs/` 规格文档 → 独立挑刺内审 → 用户确认后分批或按隔离工作区派发 | 规格定稿获批，准备进入派发 |
| **审阅既有方案** | 用户给出一份现成方案，问靠不靠谱或有没有漏点 | 对照工作区真实代码与 `AGENTS.md` / `GEMINI.md` / `DESIGN.md` 挑出事实冲突、漏用基建与边界漏洞 | 输出问题清单与修订建议 |

**中途升级**：执行中发现要动高风险模块（并发与后台任务、数据存储格式与迁移、文件删除等不可逆操作、鉴权/权限/支付等安全敏感逻辑、对外 API 与数据契约、打包发布与升级，以及开发约定里标为高风险的目录）、改动超出原定文件，或冒出新的产品取舍时，停下来升级到 `L2 / L3` 重新对齐，不硬着头皮做完。`L1` 改动只要碰到高风险模块，仍交给 `saki-code-review` 把关。

## 工作流

### 1. 代码事实与规范前置核对

1. 检查当前会话是否已掌握目标模块的真实路径、可复用公共组件/共享模块以及项目规定的局部快测命令；若尚不清楚，先按 `saki-explore` 只读查实，严禁凭猜测编造路径。
2. 若仓库存在 `AGENTS.md`、`GEMINI.md` 或 `DESIGN.md`，先核对架构分层、设计令牌、测试隔离与打包分发方面的硬约束。
3. 开工前运行一次 `PREFS get saki-plan --host <宿主>`，偏好里的要求（如用子 Agent 模式、不做默认挑刺）优先于本 Skill 的默认做法；读取失败时按默认继续。
4. 开工快检：运行 `git fetch --quiet` 和 `git status -sb`，确认当前在哪个分支和工作目录、本机主干和云端是否一致、有没有别人没提交的改动。一切正常时不提；有问题用一句话告诉用户，再决定在哪里动手。
5. 若 `AGENTS.md` / `GEMINI.md` 有标题含 `saki-dev` 的开发约定小节：快测与门禁命令直接写进验证标准和契约，禁改目录写进契约的禁改范围，可选的 `重构建` 触发目录与 `文件上限` 同步写进构建控频与拆分红线；改动涉及高风险目录时按中途升级规则处理并安排审查。没有这一节时按上面的默认高风险清单判断，可建议用 `saki-govern` 补上。

### 2. 用平实语言讲清方案（L2 / L3）

参考 [方案可读性标准与派发模板](references/plan-rubric.md)，围绕四个核心问题写清楚（若落盘到 `docs/`，沿用目标仓库原有的标题风格，不强套固定模板词）：

1. **要解决什么与外部可见变化**：对比改动前后用户看到的操作、界面或输入输出具体变成什么样。
2. **改动范围与现成基建复用**：写明直接复用仓库哪套公共组件、共享类型或函数，改哪几个文件（写成路径或通配符，后面审查时直接拿来比对）、为何新建文件，并明确列出**本期不做**的边界。
3. **关键取舍与异常、安全、兼容、打包边界**：有多种做法时用日常语言说明利弊与推荐项；交代空状态、中途取消，权限校验与外部输入处理，旧数据能否读取与如何迁移、对外接口是否保持兼容，以及脱离开发目录后的正式打包运行边界（如资源加载、权限与条件编译）。
4. **分层验证标准**：区分“执行器改完跑的局部快测命令”与“合并前统一跑一次的全量/端到端/打包门禁”；验证不仅测最终状态，按改动类型写清过程不变量与关键响应指标（如交互中途状态、并发时序或真实规模下的耗时预算）。

### 3. 方案内审与关键问题确认

1. **自检与默认挑刺**：逐一核实方案中引用的文件路径在仓库中真实存在。`L2 / L3` 方案给用户看之前，默认用 `invoke_subagent` 派发一个全新只读子 Agent **`saki-reviewer`**（未注册时用 `research`）挑刺，重点看事实错误、漏用的现成基建、边界和兼容问题，`L3` 再加上并发、状态迁移与打包盲区。**仅当用户在对话里显式要求用其他 CLI 挑刺时**，才改走 `saki-delegate`（`--role critique --runner <显式指定的 CLI>`，未指明模型时先弹出模型选择卡片）。把成立的问题改进方案，回来后确认 `git status` 没有变化。`L1` 不做挑刺。
2. **向用户确认关键决定**：首次提交 `L2 / L3` 方案时，先用一句话交代挑刺发现了什么、改了哪里、哪些意见没采纳及原因，再用几句清晰直白的话点出最核心的做法与 1–2 个待拍板选择题（需要多选项对齐时优先用 `ask_question`），确认用户真正理解并认可接下来要做的事后再动手。若无未决疑问且用户团队约定低摩擦推进，说明所选默认方案后直接执行。

### 4. 严格契约派发与并行隔离

方案确认后进入实现：

- **先保护工作区**：写模式派发前确认工作区干净（`git status` 无未提交改动），或在独立隔离工作区中执行。用户自己有未提交改动时，先问清是提交、暂存还是另开隔离工作区，不让执行器的改动和用户的混在一起。
- **按契约派发**：按 [严格派发契约与执行快规则](references/plan-rubric.md#3-审批通过后的严格派发契约含执行快规则) 组装提示词，把必复用基建、允许修改的文件、禁改范围和**测试控频纪律**写进契约：
  - **默认闭环**：普通模式下由当前会话自己实现（或按需派发 `saki-coder`）；子 Agent 模式下用 `invoke_subagent` 派发插件内置的 **`saki-coder`**（未注册时用 `self`）。
  - **显式跨 CLI**：仅当用户在对话里显式指定了外部 CLI 时，才经 `saki-delegate`（`--role implement --runner <CLI>`）派发，未指明模型时先弹出模型选择卡片。无论谁实现，都遵守这份快规则。
- **多任务并行隔离**：若同时推进多条互不依赖的任务，先确认各任务修改的热点文件不重叠：
  - 使用 Antigravity 原生 `saki-coder` 子 Agent 时，优先传 `Workspace: "share"`（共享仓库目录的独立工作副本），省去手工管理 Worktree；
  - 需要手工建 Git Worktree（例如派发外部 CLI）时，统一建在同级父目录下（不要嵌套建在主仓库目录内），并记下每条任务的分支名与 Worktree 路径供收尾合并；原生重型工程可用写时复制（如 macOS APFS `cp -cR`）克隆主仓库构建目录。
- **验收执行结果，不只听自报**：先用 `REVIEW_HELPER --allow <契约里允许的路径>` 检查有没有越界改动，再看测试有没有被删除、跳过或弱化，然后亲自跑一次契约里的局部快测（秒级，用来核实结果）；慢测试不在这一步重复跑。执行器说“基线本来就失败”时，在主干上跑同一条命令核实。随后主动衔接 `saki-code-review`，不用等用户点名：`L2 / L3` 实现完成后默认直接进审查（低风险走轻量档，命中 `[高风险目录]`、`[禁改目录]`、`[超出方案允许范围]` 或 `[文件膨胀告警]` 走独立深审）；`L1` 改动只要命中上述任一标记同样直接进审查。

### 5. 收尾合并

审查通过（或未触发审查条件的极小 `L1` 快测通过）后，按 [收尾合并清单](references/plan-rubric.md#4-收尾合并清单) 完成最后一步：在待合并分支上跑一次合并门禁；门禁失败先判断是不是本次改动引入的；`L2 / L3` 改动合并前衔接 `saki-docs` 按真实 diff 检查受影响的项目活文档（先列更新清单请用户确认后再落盘）；按仓库约定提交合并（执行器不自行提交）；多个 Worktree 按依赖顺序逐个合入，全部合入后再跑一次门禁；最后清理已合入的 Worktree，并处理 `L3` 规格文档的去留。

## 输出与后续衔接

方案阶段输出精炼方案与待拍板问题后停止；派发实现完成后交付修改摘要与局部快测结果；收尾阶段交付门禁结果与合并状态。

| 下游意图 | 衔接动作 |
| --- | --- |
| 缺陷原因还不清楚 | 进入 `saki-bug-fix` 先找根因；修复面大时带着根因和排查清单回到这里写方案 |
| 对高风险或核心产品代码做独立把关 | 进入 `saki-code-review`，把契约里允许修改的路径一并交给它比对 |
| 写方案时发现某块底层调用链还没摸清 | 先用 `saki-explore` 局部查实代码锚点 |
| 合并后清理并行 Worktree | 进入 `saki-govern` 盘点 Worktree，只清理确认可清理的那几个 |
| 功能开发完成需要同步项目活文档 | 进入 `saki-docs` 按真实 diff 评估并增量更新受影响文档 |

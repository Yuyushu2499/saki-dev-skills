# saki-comment

`SKILL_DIR` 指当前 Skill 的绝对目录；`<python>` 指 Python 3.10+（macOS/Linux 通常为 `python3`，Windows 通常为 `py -3`）；`COMMENT_HELPER` 是 `<python> "$SKILL_DIR"/scripts/comment_helper.py` 的简写。

## 核心规则

- **严禁改动任何可执行逻辑**：本 Skill 只允许新增、修改或删除注释与文档字符串（Docstring），**绝对不修改代码逻辑、变量名、控制流或导入语句**（Python 修改后可通过语法/AST 与单测验证零行为变更）。
- **默认尽量使用中文，必要之处保留英文**：注释正文使用简洁自然的简体中文；专有技术术语、函数/参数/类型名、错误码、协议名与各语言原生标准标签（如 `Args:`、`@param`、`TODO`）保留英文。
- **函数/类注释遵循各语言原生标准**：严格按目标语言生态格式书写（Google Python Docstring / TSDoc / JSDoc / GoDoc / Rustdoc / Javadoc / Doxygen），不自造奇怪格式，也不在函数头堆砌作者与日期（`git blame` 已记录）。详见 [多语言注释书写规范](references/comment-standards.md)。
- **行内注释只解释「Why」，绝不翻译「What」**：核心函数内部只给**关键代码块**（业务约束、边界特判、并发/时序前提、为什么不用更直观写法、复杂状态流转与算法意图）加精炼注释，严禁逐行翻译代码字面意思。
- **主动清理 5 类不合理注释**（删劣留优，而不是只在旧注释旁边再堆新注释）：
  1. **误导/过期注释**：与当前真实代码行为矛盾的旧注释（最危险，优先修正或删除）；
  2. **复述字面的废话注释**：如 `# i 加 1`、`// 返回结果`、`// 遍历数组`（直接删除）；
  3. **大段被注释掉的死代码**：历史代码由 Git 保存，直接删除，不留僵尸代码块；
  4. **无信息量模板 / 作者日期注释**：如 `@author`、`Created on ...`、仅把参数名照抄一遍的空洞注释（删除或改写为真实语义与约束）；
  5. **过度密集的逐行注释**：收拢为 1–2 行段落级意图说明。
- **先确认范围再批量动手**：接手整个项目或大目录补注释时，先用脚本扫描出缺失注释的核心文件与疑似不合理注释分布，向用户列出拟处理范围与优先级，经确认后分批处理，避免一次制造失控的大规模 diff。

## 先选工作模式

| 模式 | 适用场景 | 执行路径 | 默认停止点 |
| --- | --- | --- | --- |
| **老项目接手补注释（Bootstrap）** | 接手无注释或注释杂乱的仓库准备二开 | `COMMENT_HELPER` 扫描全仓 → 按核心模块排优先级请用户确认范围 → 精读源码补函数与核心块注释 + 清理不合理注释 → 验证零逻辑改动 | 交付已处理文件、补全与清理汇总 |
| **劣质注释专项清理（Audit & Clean）** | 代码里充斥过期注释、AI 废话注释或大段注释死代码 | 扫描疑似劣质注释并逐处核对真实逻辑 → 删废话/死代码、修正误导注释、补齐关键 Why 注释 → 验证 | 输出清理与替换报告 |
| **定向文件 / 本次改动补注释** | 用户指定 1–N 个文件，或针对当前 `git diff` 补齐并校准注释 | 精读目标文件/改动块 → 补规范中文注释并顺手清理不合理注释 → 语法与快测核验 | 完成目标范围注释更新 |

## 工作流

### 1. 客观扫描缺失注释与疑似不合理注释

```text
# 扫描整个仓库（遵循 .gitignore，自动跳过测试或生成目录可用 --exclude）
COMMENT_HELPER --workspace "<项目路径>"

# 仅扫描指定子目录或文件
COMMENT_HELPER --workspace "<项目路径>" --path src/core --path src/export
```

脚本会客观报告：
- 缺少文档注释的函数/类清单（重点标出**核心长函数**，默认 `>= 20` 行）；
- 疑似不合理注释候选（大段注释掉的代码块、无上下文空洞 `TODO`、作者/日期模板注释、冗长装饰分隔线等）。

### 2. 确认范围与分层策略

阅读 [多语言注释书写规范](references/comment-standards.md)。如果扫描涉及多个目录或超过 5 个文件，先向用户呈现简明清单（按核心入口/复杂模块优先排序），确认本次先处理哪几个目录或文件后再开改。

### 3. 精读真实逻辑，补合理注释 + 删不合理注释

逐文件精读代码后再下笔（绝不凭函数名猜逻辑）：

1. **函数与类文档注释**：
   - 公开接口、核心业务函数、跨模块入口、复杂内部函数：按语言原生规范写清**职责摘要、关键参数约束、返回值语义与异常/副作用边界**；
   - 1–3 行自解释极简函数（如简单 getter/setter）：不强塞模板，保持代码清爽。
2. **核心函数内部关键代码注释**：
   - 只在非显而易见处写简洁中文注释：说明**为什么这样做、依赖什么前置条件、处理什么边界/并发/兼容场景、关键算法步骤的目标**。
3. **清理与替换不合理注释**：
   - 遇到与当前代码不符的旧注释：对照真实代码修正或删除；
   - 遇到复述字面的废话注释、大段注释死代码、无意义分隔线与作者/日期套话：直接删除。

### 4. 零逻辑改动核验

1. 用 `git diff` 核对全部变更，确认**没有任何可执行代码被意外改动**。
2. 运行目标语言的语法检查、类型检查或局部快测（如 Python `py_compile` / `pytest`、TS `tsc --noEmit`、Go `go test`），确认行为 100% 不变。

## 输出与后续衔接

完成后简明汇报：处理的目录/文件数、补全的函数/核心逻辑注释数量、清理/修正的不合理注释类型及验证结果。

| 下游意图 | 衔接动作 |
| --- | --- |
| 注释补齐后同步生成或更新项目架构文档 | 进入 `saki-docs` 基于已梳理清楚的代码生成活文档 |
| 验证通过准备中文提交并推送到云端 | 进入 `saki-ship` 完成安全预检与中文 commit + push |

# Saki Dev 通用工程约定

以下规则随 `saki-dev-skills` 插件启用自动生效，保持简洁克制，不影响目标仓库自身的 `AGENTS.md` / `GEMINI.md` 优先级。

## 1. 测试通过后自动中文提交并推送（saki-ship）
- 每次完成一项独立功能或修复、并确认对应验证测试全部通过后，按 `saki-ship` 流程执行交付预检、提交并推送到云端仓库。
- **提交信息规范**：使用 `Conventional Commits` 英文类型前缀（`feat:`、`fix:`、`refactor:`、`docs:`、`test:`、`chore:` 等）+ **简体中文描述**，仅必要的技术专有名词、符号名与文件名保留英文。
- **保护分支红线**：位于开发分支（如 `dev`、`feat/*`、`fix/*`）且无敏感文件告警或远端冲突时可直接自动提交推送；位于 `main` / `master` 保护分支或存在异常告警时，必须先向用户确认，绝不擅自直推主干或强推（`--force`）。

## 2. 编写与修改代码时自带合理中文注释并清理劣质注释
- 新增或修改公开接口、核心函数/类及函数内部关键代码块时，按目标语言原生标准（Google Python Docstring / TSDoc / JSDoc / GoDoc / Rustdoc / Javadoc / Doxygen）同步添加简洁中文注释（必要专有名词、类型与标准标签保留英文）。
- 行内注释只解释 **Why**（业务约束、边界特判、并发/时序前提、兼容原因与算法意图），绝不复述代码字面 **What**，也不在函数头写作者与日期。
- 修改代码过程中若顺手遇到与当前逻辑矛盾的过期注释、复述字面的废话注释或大段被注释掉的死代码，主动删除或替换为准确注释；批量治理历史无注释项目时激活 `saki-comment`。
